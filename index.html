01.1 — sistemas de versão

Centralizado e distribuído: qual a diferença na prática?

No centralizado, o histórico fica num servidor. No distribuído, cada desenvolvedor tem uma cópia completa localmente.

Centralizado / CVCS

Um servidor guarda o histórico inteiro.

O desenvolvedor baixa só a versão que precisa trabalhar. Sem conexão com o servidor, não dá pra commitar, ver o log ou criar branch. SVN e CVS funcionam assim.

Distribuído / DVCS

Cada clone já é um repositório completo.

Todo desenvolvedor tem o histórico inteiro na máquina dele. Dá pra trabalhar offline, e se o servidor cair os dados não somem. É assim que o Git funciona.

01.2 — arquitetura local

As três áreas do Git que você precisa conhecer.

Antes de rodar qualquer comando, é importante entender onde o Git guarda as coisas e por quê.

01 · working directory

onde você edita

A pasta normal do projeto no seu computador. Arquivos modificados aqui ainda não estão sendo rastreados pelo Git.

→
02 · staging area

onde você seleciona

Uma área intermediária onde você escolhe quais mudanças vão entrar no próximo commit. É o git add que move os arquivos pra cá.

→
03 · .git/

onde fica salvo

O repositório local de verdade. Cada commit vira um snapshot identificado por um hash SHA-1 e fica guardado aqui.

01.3 — um pouco de história

Como o Git surgiu em dez dias.

2002

O kernel Linux começa a usar o BitKeeper

Ferramenta proprietária cedida de graça pro desenvolvimento do kernel. Funcionou por três anos.

abril / 2005

A licença do BitKeeper é revogada

Sem uma alternativa boa no mercado, Linus Torvalds parou o desenvolvimento do kernel pra criar sua própria ferramenta.

7 / abril / 2005

Primeiro commit do Git, feito no próprio Git

Dez dias depois do início do desenvolvimento. Os requisitos principais eram velocidade, integridade dos dados e suporte a branches paralelas.

2008

GitHub é lançado

Adicionou hospedagem de repositórios com interface web, issues e pull requests. Ajudou bastante na adoção do Git em projetos open source.
