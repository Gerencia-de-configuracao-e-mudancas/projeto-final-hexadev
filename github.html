Git é a ferramenta. GitHub é o lugar.

Versionar é local. Colaborar é remoto. Aqui você liga as duas pontas — com autenticação que não vaza e automações que rodam sozinhas.

git vs github https · ssh actions / ci-cd
git vs github → autenticação
04.1 — confusão clássica

Não é a mesma coisa. Nem é da mesma empresa.

Git foi criado em 2005 por Linus Torvalds. GitHub foi fundado em 2008 e hoje pertence à Microsoft.

git

software local, instalado no seu computador.

Open source. Roda sem internet. Gerencia o histórico em .git/ e não conhece nuvem alguma por padrão.

github

plataforma web que hospeda repositórios git.

Adiciona pull requests, issues, code review, actions, packages e uma interface visual. Não é a única — GitLab e Bitbucket fazem o mesmo papel.

04.2 — autenticação

Conectar o repositório local ao remoto.

Senha não funciona mais. Você precisa de um token (HTTPS) ou de um par de chaves (SSH).

opção a · https + pat

token de acesso pessoal

Mais simples de começar. Você gera um PAT no GitHub e usa no lugar da senha. Bom para máquinas temporárias.

→
opção b · ssh

par de chaves criptográficas

Padrão da indústria. Gera id_ed25519 local, coloca a pública no GitHub e nunca mais digita senha.

→
resultado

push e pull sem fricção

Independente da opção, o objetivo final é o mesmo: sincronizar commits sem interrupção.

configurando ssh do zero
$ ssh-keygen -t ed25519 -C "seu@email.com" Generating public/private ed25519 key pair. $ cat ~/.ssh/id_ed25519.pub # copie esta chave em github.com/settings/keys $ git remote add origin git@github.com:user/repo.git $ git push -u origin main
04.3 — automação

GitHub Actions: o servidor que trabalha enquanto você dorme.

Um arquivo YAML em .github/workflows/ faz o GitHub rodar testes, build e deploy a cada push.

.github/workflows/ci.yml
name: ci on: [push, pull_request] jobs:   test:     runs-on: ubuntu-latest     steps:       - uses: actions/checkout@v4       - uses: actions/setup-node@v4         with: { node-version: 20 }       - run: npm ci       - run: npm test

ci — continuous integration

Rodar testes a cada push.

Pega bugs antes do merge. Quanto mais cedo o feedback, mais barata a correção.

cd — continuous deployment

Subir código para produção automaticamente.

Merge na main dispara o deploy. Sem intervenção manual, sem pasta zipada por FTP.
